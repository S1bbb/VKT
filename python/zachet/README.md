# Зачёт. Списки Python против массивов numpy

Доп. вопрос: **в чём разница между питоновскими «массивами» (списками) и массивами numpy.**

`arrays.py` — код с доски. Запуск из папки: `py arrays.py`. Нужен `numpy` (`pip install numpy`).

Складываем поэлементно два списка по `N = 2^23 ≈ 8.4 млн` случайных чисел семью способами и меряем время `perf_counter_ns` (делим на `1e6` → миллисекунды).

## Что получилось (у меня, порядок величин)

| # | Способ | Время |
|---|--------|------:|
| i | цикл по индексам `M[i] = L1[i] + L2[i]` | ~1400–1600 ms |
| ii | `zip` + `append` | ~700–1000 ms |
| iii | списковое включение | ~1000–1200 ms |
| iv | numpy `dtype=object`, `L1 + L2` | ~400–480 ms |
| v | numpy `dtype=object`, `M += L2` | ~320–340 ms |
| vi | numpy `int32`, `L1 + L2` | ~140–430 ms |
| vii | numpy `int32`, `L1 += L2` | **~5 ms** |

Цифры пляшут от запуска к запуску, но картина всегда одна: чистый Python — секунда, numpy с `object` — в несколько раз быстрее, numpy с `int32` на месте — в **сотни раз** быстрее.

## Почему так

### Как устроен список Python

Список — это массив **указателей** на объекты. Каждое число — отдельный объект `int` где-то в куче (28 байт на число + 8 байт на указатель). Элементы могут быть любого типа вперемешку: `[1, 'a', 3.5]`.

Поэтому `L1[i] + L2[i]` на каждой итерации это:
- интерпретатор разбирает байткод;
- достаёт указатель, идёт по нему к объекту;
- проверяет тип (а вдруг это строка?), ищет у него `__add__`;
- создаёт **новый** объект `int` под результат.

И так 8 миллионов раз.

- **(i) индексы** — самый медленный: на каждом шаге ещё `range`, два обращения по индексу и запись по индексу.
- **(ii) append** и **(iii) включение** — быстрее, `zip` отдаёт пары сразу, без индексации. Включение обычно чуть быстрее `append` (нет поиска метода `.append`), но на таком объёме разницу съедают выделение памяти и сборщик мусора — у меня они шли примерно вровень.

### Как устроен массив numpy

`np.array` — один **сплошной кусок памяти** с элементами **одного типа** (`dtype`) и фиксированного размера. `int32` — ровно 4 байта на число, без объектов и указателей. 8.4 млн чисел = 32 МБ подряд.

Операция `L1 + L2` — **векторизованная**: один вызов уходит в цикл на C, который просто идёт по памяти и складывает машинные числа. Никакого интерпретатора и проверки типов на каждом элементе, процессор ещё и использует SIMD (несколько сложений за такт).

- **(iv)/(v) `dtype=object`** — numpy хранит те же указатели на питоновские `int`. Цикл уже на C, поэтому быстрее, чем (i)–(iii), но каждое сложение всё равно — вызов питоновского `__add__` и новый объект. Отсюда «всего» в 3–4 раза.
- **(vi) `int32`, `L1 + L2`** — сложение настоящих чисел на C. Большая часть времени тут — выделить новый массив на 32 МБ под результат `M`.
- **(vii) `int32`, `L1 += L2`** — сложение **на месте**, результат пишется прямо в `L1`, новой памяти не надо. Поэтому ~5 ms — это почти чистое время пробежать по памяти.

Разница между `+` и `+=`: `M = L1 + L2` создаёт новый массив, `L1 += L2` меняет существующий. У списков, кстати, `+` и `+=` вообще значат **склеивание**, а не поэлементное сложение: `[1, 2] + [3, 4] == [1, 2, 3, 4]`.

### Зачем `Upper = 2 ** 30`

`int32` хранит числа от `-2^31` до `2^31 - 1`. Сумма двух чисел меньше `2^30` гарантированно меньше `2^31`, поэтому не переполнится. Если взять числа больше — numpy **молча** переполнится: `np.array([2**31 - 1], dtype='int32') + 1` даст `-2147483648`. Питоновский `int` переполниться не может — у него длинная арифметика. Это плата за скорость.

## Коротко для ответа

| | список Python | массив numpy |
|---|---|---|
| Что хранит | указатели на объекты | сами значения подряд в памяти |
| Типы элементов | любые, вперемешку | один `dtype` на весь массив |
| Размер | меняется (`append`, `pop`) | фиксирован, при изменении — новый массив |
| Память на `int` | ~28 байт объект + 8 указатель | 4 байта (`int32`) / 8 (`int64`) |
| `a + b` | склеивание списков | поэлементное сложение |
| Операции | циклом в интерпретаторе | векторизованно, цикл на C (+SIMD) |
| Переполнение | нет, числа любой длины | есть, молча оборачивается |
| Скорость на 8 млн | ~1 с | ~5–150 ms |

Вывод: список — универсальный контейнер для чего угодно; numpy — для больших однородных числовых данных, где важна скорость и память. С `dtype=object` numpy теряет почти всё своё преимущество.
